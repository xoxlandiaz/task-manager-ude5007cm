# db/ — база данных PostgreSQL

Таблицы: users, projects, project_members, tasks, comments. ER-диаграмма: [docs/er-diagram/er-diagram.md](../docs/er-diagram/er-diagram.md).

| Путь | Что это |
|---|---|
| `migrations/001–005_*.sql` | создание таблиц, по одной миграции на таблицу |
| `seeds/001_demo.sql` | демо-данные: 3 пользователя, 2 проекта, 7 задач, 4 комментария |
| `schema.sql` | все миграции одним файлом, для чтения и отчёта |

## Как применить

```bash
for f in db/migrations/*.sql; do psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$f"; done
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f db/seeds/001_demo.sql   # по желанию
```

Демо-вход: `aki@example.com` / `Password123!` (у всех трёх пользователей один пароль).

## Что в каждой миграции и почему (для viva)

**001 users.** `id` через `GENERATED ALWAYS AS IDENTITY`: это стандарт SQL и современная замена `SERIAL`. `email UNIQUE` не даёт зарегистрироваться дважды, а `CHECK (email = lower(email))` заставляет бэкенд приводить email к нижнему регистру, иначе `Aki@x.com` и `aki@x.com` были бы разными людьми. Пароль хранится только как bcrypt-хеш в `password_hash`.

**002 projects.** `owner_id` ссылается на `users` с `ON DELETE CASCADE`: удалил аккаунт, исчезли и твои проекты. Здесь же функция `set_updated_at()` и триггер: при любом `UPDATE` поле `updated_at` обновляется само, бэкенду не нужно об этом помнить. Индекс на `owner_id`, потому что PostgreSQL не индексирует внешние ключи автоматически.

**003 project_members.** Таблица-связка для M:N «пользователь ↔ проект». Составной первичный ключ `(project_id, user_id)` запрещает добавить одного человека в проект дважды. `role` ограничен значениями `owner` и `member`: по нему бэкенд проверяет, кто может удалять проект или приглашать людей. Отдельный индекс на `user_id` ускоряет «мои проекты» (по `project_id` уже работает PK).

**004 tasks.** `project_id` с CASCADE: задача без проекта не существует. `assignee_id` и `created_by` с `SET NULL`: если пользователь удалён, задача остаётся, просто без исполнителя. `status` и `priority` ограничены через `CHECK`, а не `ENUM`, потому что CHECK легко изменить следующей миграцией. Индексы на `project_id`, `assignee_id`, `status` под типичные фильтры канбан-доски.

**005 comments.** Комментарий принадлежит задаче (CASCADE) и автору. `CHECK (char_length(trim(body)) > 0)` не пропускает пустые комментарии даже если валидация на бэкенде пропущена: это вторая линия защиты.

**Общее.** Все таблицы в 3НФ: данные о пользователе только в `users`, остальные хранят его `id`. Миграции написаны с `IF NOT EXISTS` и `CREATE OR REPLACE`, поэтому повторный запуск не падает.

## Проверено

На PostgreSQL 16, пустая база: миграции применяются без ошибок и повторно; сид идёт дважды подряд (в начале `TRUNCATE ... RESTART IDENTITY`); триггер `updated_at` срабатывает; `CHECK` отклоняет `status = 'bad'`; удаление пользователя обнуляет `assignee_id`; удаление проекта каскадно удаляет его задачи и комментарии; `schema.sql` применяется к пустой базе.
